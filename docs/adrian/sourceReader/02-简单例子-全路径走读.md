# 02 简单例子 —— 全路径走读

> 本篇为**第二层**：选一个真实、最小、可运行的成功场景（`POST /v1/chat/completions`），从入口追踪到结果。只走主成功路径，脱敏输入输出，真实文件/函数/参数/返回值。

---

## 0 场景定义

**请求**：用户用 OpenAI SDK 向本地 gateway 发送一次普通聊天完成请求。

```bash
curl -X POST http://127.0.0.1:3001/v1/chat/completions \
  -H "Authorization: Bearer freellmapi-abc123..." \
  -H "Content-Type: application/json" \
  -d '{
    "model": "auto",
    "messages": [{"role": "user", "content": "Hello"}],
    "stream": true
  }'
```

**预期结果**：SSE 流式返回 `data: {"id":"chatcmpl-...","choices":[{"delta":{"content":"Hi there!"}}]}`，最终 `data: [DONE]`。

**环境假设**：
- Server 已启动，DB 已初始化，至少有一个 provider (如 Google Gemini) 配置了有效 key 且处于 `healthy` 状态
- Fallback 链里该模型优先级最高，且未触及任何限流
- Desktop 模式端口为 31415，但逻辑完全一致

function requireInferenceAuth(req: Request, res: Response): ResolvedAuth | null {
  const auth = resolveAuth(extractApiToken(req));  // lib/system-prompt.ts:resolveAuth
  if (!auth) {

### 3.2 限流预检：`ratelimit.ts` 的闸门串联（在 `selectKeyForModel()` 内依序执行）

不存在单一入口的「检查+预留」函数；预检是 `selectKeyForModel()` (router.ts:1582) 对每把候选 key 依序调用的一串布尔闸门（顺序即源码顺序，router.ts:1660-1677）：

```typescript
// server/src/services/ratelimit.ts —— 各闸门定义行
isOnCooldown(platform, modelId, keyId)            // =1255 冷却：rate_limit_cooldowns 表 + 内存
canUseProvider(platform, keyId)                   // =665  provider 账号级日请求上限
canUseProviderMinute(platform, keyId)             // =689  provider 账号级每分钟预算
canUseKeyConcurrency(platform, keyId)             // =120  key 在途并发上限（默认无上限）
canMakeRequest(platform, modelId, keyId, limits)  // =312  RPM + RPD（limits 来自模型行，NULL=不限）
canUseTokens(platform, modelId, keyId, est, lim)  // =334  TPM + TPD，按 estimatedTokens 预留
canUseProviderTokens(platform, keyId, modelId, est)// =783 provider 账号级日 token 上限
checkMonthlyBudget(keyId, est)                    // services/key-budget.ts:92 月度预算（#1158）
// 全过之后才预留：
acquireLease(platform, modelId, keyId, tokens)    // =127  取 in-flight 租约，返回 leaseId
```

- 每个闸门返回 boolean（或 `{allowed, ...}` 结构体），不通过时在诊断里 `note('rpm/rpd-limit')` 之类的类别后换下一把 key；`retryAfterMs` 属于失败记账路径 `getCooldownDecisionForLimit()`（=1112），不在预检里。
- 计数 = 内存滑窗 + `rate_limit_usage` 历史 + **在途租约求加和（provisional）**：`canMakeRequest`/`canUseTokens` 会把 `leases` Map 里的预留算进当前窗口，闭合「检查后扣减」竞态。

**关键常量**（services/ratelimit.ts:32-33）：
- `MINUTE = 60_000`、`DAY = 24 * 60 * MINUTE`——RPM/TPM 用 `MINUTE` 滑窗，RPD/TPD 用 `DAY` 滑窗；不存在名为 `*_WINDOW_MS` 的常量
- 冷却阶梯 `COOLDOWN_DURATIONS = [2min, 10min, 1h, 24h]`（=879，按 24h 内第几次命中）；操作者可设 settings 键 `routing_cooldown_ceiling_ms`（`COOLDOWN_CEILING_KEY`=896）封顶，范围 `MIN/MAX_COOLDOWN_CEILING_MS`=1min~1day（897-898）
- 402 冷却 `PAYMENT_REQUIRED_COOLDOWN_MS = DAY`（=963）
- key 并发上限是 **opt-in**：`getKeyConcurrencyLimit(platform)`（=98）读 env `MAX_CONCURRENT_REQUESTS_PER_KEY[_<PLATFORM>]`，未设置返回 `null` = 无上限，`canUseKeyConcurrency`（=120）对无上限直接放行——代码里没有内置的并发数字默认值

### 3.3 选中路由后：回退主循环 `runFallbackLoop()` (lib/fallback-loop.ts:1348)

router 侧不存在 `streamChatCompletion()` generator；流式尝试循环在 `lib/fallback-loop.ts`，每个 surface 通过 `FallbackHooks` 注入自己的 route/dispatch 闭包（`dispatch` 契约在 fallback-loop.ts:1318）。`/v1/chat/completions` 的一轮尝试按真实调用序列：

```typescript
// 概念示意（调用序列与源码阶段一一对应，非逐行源码）：
runFallbackLoop(hooks)                       // fallback-loop.ts:1348 → 1367 runFallbackLoopAttempts
  └─ for attempt in 0..maxRetries(默认20, FALLBACK_MAX_RETRIES=69; 墙钟预算默认 45s,
       DEFAULT_FALLBACK_TIME_BUDGET_MS=172, 可被 settings `fallback_time_budget_ms`/env 覆盖):
       route = hooks.route(attempt)          // proxy 闭包 → router.ts:2152 routeRequest(...)
       await hooks.dispatch(route, attempt, ctx)
       // proxy 派发闭包（routes/proxy.ts:2453 起）：
       //   const gen = route.provider.streamChatCompletion(apiKey, messages, modelId, opts, quotaCtx)
       //   for await (const chunk of gen) → 边收帧边 res.write(SSE)
       //   流毕对累计文本做工具调用救援 rescueInlineToolCalls(...)   // routes/proxy.ts:2618
       //   流毕成功 → recordUpstreamSuccess(route, totalTokens, state)   // routes/proxy.ts:2764
       //     └─ recordRequest(=821) + recordTokens(=833) 写实账 + recordSuccess(=router.ts:310) 减惩罚
       //   抛错     → recordRetryableFailure(=fallback-loop.ts:440)（认证类走 recordAuthFailure=651）
       //     └─ 冷却决策 getCooldownDecisionForLimit(=ratelimit.ts:1112) + setCooldown + 加惩罚
       // finally → route.release?.()         // fallback-loop.ts:1652 释放并发租约与月度预算
```

失败则循环取 `skipKeys/skipModels` 更新后的下一候选，直到成功、客户端断开或预算/次数耗尽。

## 9 失败路径预览（第三层展开）

主成功路径之外，以下分支在第三层详细拆解：

1. **限流预检失败** → `selectKeyForModel()` 闸门不通过（`note('rpm/rpd-limit')` / `'tpm/tpd-limit'` / `'cooldown'` 等类别）→ 换下一把 key，全 key 都不过则 router 尝试下一候选
2. **上游 429/5xx** → `recordRetryableFailure()` (fallback-loop.ts:440) + router 侧 `recordRateLimitHit()`(=303)/`recordModelFailure()`(=285) 加惩罚、`setCooldown` → `runFallbackLoop` 重试下一模型（最多 20 次 / 默认 45s 墙钟预算，`DEFAULT_FALLBACK_TIME_BUDGET_MS`=172）
3. **工具调用格式错误** → `tool-validate.ts:invalidToolCallReasons` → 自动修复或返回错误
4. **Context window 溢出** → `applyTokenBudget` 截断 messages / 跳过该模型
5. **所有模型耗尽** → `RouteError` with `diagnostics[]` → `summarizeExhaustion()` 生成客户端可读错误
6. **客户端中断** → `isClientAbortError` → 不计入失败、不触发冷却、释放租约
