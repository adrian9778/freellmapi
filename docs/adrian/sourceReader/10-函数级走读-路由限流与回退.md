# 10 · 函数级走读：路由、限流与回退

> 03/04 篇讲的是机制与关系，本篇逐函数拆解主链路上 9 个核心函数：**每个函数给出签名、职责、内部分步、关键代码摘录与调用关系**。函数选取标准：删除它整条链路就断。行号偏移均相对符号本身（`函数名+N`），绝对行号见文末索引。
>
> 阅读顺序建议：`routeRequest` → `orderChain`/`scoreChainEntry`（打分排序）→ `selectKeyForModel`（选 key）→ `canMakeRequest`/`getCooldownDecisionForLimit`（限流判定）→ `runFallbackLoop`/`recordRetryableFailure`（失败反馈）。前向调用关系是：
>
> ```
> proxy 面 ─► runFallbackLoop ─► hooks.route ─► routeRequest ─► orderChain ─► scoreChainEntry
>                                        │              └─► selectKeyForModel ─► can* / isOnCooldown / acquireLease
>                                        └─ hooks.dispatch 失败 ─► recordRetryableFailure ─► setCooldown
> ```

## 1. `routeRequest` — 路由总入口（router.ts）

```ts
export function routeRequest(
  estimatedTokens = 1000,          // 输入估算 + 封顶输出预留
  skipKeys?: Set<string>,          // "platform:modelId:keyId"，本次请求已失败的
  preferredModelDbId?: number,     // sticky session / 显式 pin
  requireVision = false, requireTools = false, requireStructured = false,
  skipModels?: Set<number>, skipPlatforms?: Set<string>,
  prefetchedChain?: ChainRow[],    // 调用方已取好的链（省一次链缓存读）
  exactOutputReserve = 0,          // 客户端真实 max_tokens（区别于封顶预留）
  task?: 'code' | 'chat',
): RouteResult
```

**职责**：从活动链中选出一个「此刻真有 key 能服务」的 RouteResult；选不出则抛 `RouteError`(429) 并携带每个候选的处置记录。**返回即预留**（lease + monthly budget 已在内部扣下），调用方必须 eventually 调 `route.release()`。

**内部分步**（`routeRequest+1~+21`）：

1. **+2~+4**：读策略；非 priority 时先 `refreshStatsCache(db)`（60s TTL 的统计聚合，priority 模式用不到不刷）。
2. **+5~+7**：`(prefetchedChain ?? getActiveChain(db)).filter(e => e.enabled)` → `orderChain(..., sampled=true, task)`。sampled=true 意味着每次调用做 Thompson 采样，同一条链两次调用可以给出不同顺序——这是探索的来源。
3. **+27~+58 探索槽**：bandit 策略 + 探索开关 + 非降级模式 + `Math.random() < EXPLORE_CHANCE` 四重门后，从「样本数 < EXPLORE_MIN_SAMPLES」的模型里均匀抽一个挪到链首。**过滤镜像了主循环全部闸门**（+32~+45：skipModels/skipPlatforms/vision/tools/toolBenched/structured/context/tpm），否则探索位会浪费在一个马上会被跳过的模型上；被 `MODEL_ROUTING_OVERRIDES` 置 0 的模型**永不**当探针（+30 注释：它赢不了任何一次 bandit 对决，否则会成为永久探测目标）。
4. **+61~+86 pin/sticky**：preferred 在链里→挪到链首；不在→**从 models 表现查注入链首**（+71~+83），SQL 手工拼出 ChainRow 形状。客户端点名要的模型必须被履约，哪怕它不在活动 profile 里。
5. **+88~+110 无 key 平台预过滤**：`usableKeyCountsByPlatform` 为 0 的平台整排摘掉（这些行走主循环必然产不出路由，纯开销且污染耗尽摘要）。聚合成**一行** diag（`keylessLine`，+106），不进路由计数——这是「37 条被检查」虚报为真实候选数的修复。pin 豁免。
6. **+118~+129 软降序而非剔除**：context margin 不够的（`marginDeferred`）和屡拒 tool 的（`toolDeferred`）被**挪到队尾**而不是排除（#956/#1230 review 决策：`/v1/models` 广告的是原始窗口，客户端贴着上限打包请求是合法行为，硬剔除会把「一个被处理过的上游 400」变成「零尝试的全池耗尽」）。
7. **+141~+211 主 walk**：逐 entry 过 8 道闸门，每道被拒都 `diag.push(带原因的行)`：
   - skipModels（本次请求已判死该模型，+147）/ skipPlatforms（#788 平台级判死，+154）
   - vision/tools 能力位（+158/+165，**sticky 模型同样受限**——不能把图像轮钉死在看不见它的模型上）
   - `platformDropsResponseFormat`（+173，平台级快路径：参数会在发送前被丢掉）
   - `fitsContextWindowStrict`（+187，只比原始窗口——margin 判定已在第 6 步做过软处理；diag 行保留 `< estimated` 子串，`summarizeExhaustion` 按它归档 prompt overflow）
   - `tpm_limit < estimated`（+203：输入本身超 tpm 的模型永远塞不进一分钟，Groq 131k 上下文但 8k TPM 的实例）
   - `selectKeyForModel(entry, ...)`（+209）——返回非 null 即**函数结束**。
8. **+215~+220 耗尽**：`summarizeExhaustion(diag, getSoonestCooldownExpiry(), now, keylessSkipped)` 打包 9 桶归类 + 最近恢复时刻，抛 `RouteError(429)`，`diagnostics` 带全量 per-model 处置（这是同步「全耗尽」路径上**唯一**的失败原因记录，下游没人再记）。

**调用方**：三个 wire 面的 `hooks.route` 闭包（见 §7）。

**坑**：`estimatedTokens` 与 `exactOutputReserve` 要成对传——预留封顶（`routingReserveTokens+0`：OUTPUT_RESERVE_CAP=2000，#470「超预留会饿死路由」）防大 max_tokens 排除所有模型，exact 值只用于 margin 精确判定。

## 2. `orderChain` — 链排序双模式（router.ts:1144）

```ts
function orderChain(chain: ChainRow[], strategy: RoutingStrategy,
                   sampled = true, task?: 'code' | 'chat'): ChainRow[]
```

1. **+2~+3**：`tier = e.match_tier ?? 0`——tier 是唯一打分**不可覆盖**的排序输入（slug fallback 解析才非零），永远做外键。
2. **+4~+33 priority 分支**：`weightsFor(strategy)` 为 null（手动模式）时走遗留路径：按 priority 排 → **稠密重编号 1..N** → 加 `getPenalty(model_db_id)` → 按 `(tier, eff, priority, 原序)` 排。稠密重编号是修复「penalty 失效」bug 的关键（+14~+31 长注释）：原始 priority 间隔任意（10/20/30、1..N 挖洞），±10 的罚分在间隔面前静默无效——一个每请求必 429 的模型可以永远钉在链首。重编号后「罚 1 位」才真的是罚 1 位。
3. **+43~+48**：task 偏置（#1127），`taskAdjustedWeights` 对 fastest/reliable/custom 豁免。
4. **+51**：`applyReliabilityFloor`——低于运营可靠性地板的模型先摘掉（样本不足 `EXPLORE_MIN_SAMPLES` 的保留；若摘空则整个过滤作废，安全阀）。
5. **+53~+66 bandit 分支**：全链 `intelligenceComposite` 先算 min/max（归一化域），`scoreChainEntry` 逐个打分，按 `(tier, -score, priority)` 排。

**调用方**：`routeRequest+7`、`getOrderedFusionChain`（sampled=false，要稳定展示）。

## 3. `scoreChainEntry` — 单模型打分（router.ts:1031）

```ts
function scoreChainEntry(entry, weights, intelMin, intelMax, sampled,
                        keyCounts, headroomCfg): ScoredEntry
```

分轴逐个（每轴的实现公式在 scoring.ts，见 04 篇 §打分公式）：

| 步 | 锚点 | 内容 |
|---|---|---|
| 可靠性 | `scoreChainEntry+9~+14` | `sampled ? sampleBeta(alpha,beta) : expectedReliability(...)`——**同一个 posterior，两种读法**：路由抽签用采样（探索），仪表盘展示用期望（稳定）。community prior 折进 posterior |
| 速度 | +16 | `speedScore(tokPerSec, avgTtfbMs)`，无样本回退 SPEED_PRIOR=0.6（乐观先验保证未测模型可被探索） |
| 智能 | +17~+19 | `intelligenceScore(composite, intelMin, intelMax)`——**链内 min-max 归一**，所以 intelMin/Max 由 orderChain 统一算好传入 |
| 月度余量 | +28~+31 | `parseBudget(monthly) * max(1, keyCounts[platform])`——per-key 预算按平台可用 key 数放大（#456 与池化 monthlyUsedTokens 对齐）；headroomCfg 由调用方**读一次传进来**（+32~+35 注释：getSetting 是无缓存 SELECT，每 entry 读 = 每请求每模型两次 SQLite 往返） |
| 窗口余量 | +42~+47 | `rateWindowHeadroomFactor(modelWindowUsedFraction(...))`——rpm/rpd/tpm/tpd 实时利用率驱动的同一护栏（#899），数据来自 ratelimit 侧 5s memo 快照 |
| 合成 | +56 | **`Math.min(monthly, window)` 而不是乘**：两把尺表达同一种「快烧完了」的意见，相乘会把两头都低的模型压到 floor²，突破运营设定的地板 |
| 罚分 + 覆盖 | +57~+65 | `rateLimitFactor(getPenalty(...))` 乘子；`applyModelWeightOverride` 最后缩放（#738：置 0 = 退出 bandit 但 priority 模式仍可选） |

## 4. `selectKeyForModel` — 模型内选 key（router.ts:1522）

```ts
function selectKeyForModel(entry: ChainRow, estimatedTokens: number,
  skipKeys?: Set<string>, diag?: string[]): RouteResult | null
```

**职责**：对该模型的 key 池逐闸门走一遍，返回第一个可用 key 的完整 RouteResult（含预留）；全不可用返回 null 并往 diag 记一行「N key(s) — cooldown:2, rpm/rpd-limit:1」式的门因统计。

分步（`selectKeyForModel+1~+145`）：

1. **+4~+16**：provider 注册检查 + key 池查询：`enabled=1 AND status IN ('healthy','unknown')`——**unknown（从未测过）可用**，error/invalid 不可用。
2. **+23~+27**：模型作用域过滤（#657）：`model_scope_json` 不含该模型的 key 从池子里拿掉（不占轮转位、不烧必 403 的尝试）。
3. **+42~+60 key 排序**：`refreshStatsCache` 后 `orderKeysByScore`（#580：任一 key 有历史数据→按 per-key bandit 采样分排，让屡败 key 不再按 N 分之一概率接活）；无数据回退 round-robin 轮转（游标 `roundRobinIndex`，键含 endpoint_scope——#651 两个 relay 同 modelId 不共享游标）。#919 剩余配额加权在既有顺序上**再排一层**，平手回退原顺序。
4. **+66~+68 custom 端点锁**：custom 模型属于恰好一个 endpoint（#212），可用 key = 同 base_url 的全部 key。
5. **+70~+96 每 key 九道闸门**（顺序即语义，每道拒一把记 tally）：
   `custom-key-mismatch → already-failed-this-request → isOnCooldown → canUseProvider(日请求帽) → canUseProviderMinute(账号级分钟帽，先于 per-model 因为 NULL rpm 的模型会溜过) → canUseKeyConcurrency → canMakeRequest(rpm/rpd) → canUseTokens(tpm/tpd) → canUseProviderTokens → checkMonthlyBudget(#1158)`。
6. **+98~+106 解密**：`cachedDecrypt`（ct 变即失效的 1-entry 缓存）；抛错 ⇒ **就地 `UPDATE status='error'`** 并继续下一个 key——坏密文行不能每请求重试。
7. **+112~+136 预留与产出**：通过全部闸门才推进轮转游标、`decryptProxyUrl`（#590 per-key 代理，解密一次放进 RouteResult）、`reserveMonthlyBudget`（可能仍失败——并发写）、`acquireLease`。**`release()` 闭包 = releaseLease + budget.release**， lease 在「确定要返回这个 key」之后才拿——被拒的候选不消耗并发额度。
8. **+139~+144 失败收尾**：无可用 key 也要 `roundRobinIndex.set(rrKey, idx)`——否则下次又从同一个已耗尽的 key 开始数。

## 5. `canMakeRequest` / `canUseTokens` — 限流硬闸（ratelimit.ts:312/334）

```ts
canMakeRequest(platform, modelId, keyId,
               limits: {rpm, rpd, tpm, tpd}) → boolean
canUseTokens(platform, modelId, keyId,
             estimatedTokens, limits: {tpm, tpd}) → boolean
```

两函数同构，`canMakeRequest+6~+18` 的四步即模板：

1. `provisionalRequests/Tokens`：**in-flight 预留计入窗口**——租约代表「此刻正在发生」，属于这一分钟也属于今天（+8~+9 注释）。这是闭合「先查后改」竞态的半边（另半边是 selectKeyForModel 拿到 key 立刻 acquireLease）。
2. `requestCount/tokenCount`（`ratelimit.ts:286/299`）：**DB 优先，内存兜底**——`countPersistedRequests` 走五列复合索引点查；`withDb` 返回 undefined（无 DB，测试/内存场景）才落到 `memoryRequestCount` 滑窗。同一 `(platform,model,key,kind)` 同一时刻只有一套真相。
3. 比较：`used + inFlight >= limit`（请求）/ `used + inFlight + estimated > limit`（token 多减一个待发送的估算量）。
4. **NULL = 不限**：每道闸先判 `limits.xxx !== null`——目录没发布限额的模型不受此闸约束（由 provider 侧 429 + 冷却闭环接管）。

**调用方**：`selectKeyForModel`（路由期）、`hasOtherUsableKey`（429 降级判定）、cooldown-probe。

## 6. `getCooldownDecisionForLimit` — 冷却时长裁决（ratelimit.ts:1109）

```ts
getCooldownDecisionForLimit(platform, modelId, keyId,
  limits: {rpd, tpd}, retryAfterMs?, opts?: {quotaSignal?})
  → { durationMs, source: 'authoritative' | 'heuristic' }
```

返回「时长 + 出处」，出处决定 cooldown-probe 能不能提前探测（heuristic 可探，authoritative 永不提前——provider 自己说了等多久就等多久）。

决策树（`getCooldownDecisionForLimit+14~+55`）：

1. **+14~+22 本地端点短路**：loopback/RFC1918 base_url 的 key——**没有配额这种东西**，429 只是「此刻忙」，固定 `LOCAL_ENDPOINT_COOLDOWN_MS` 几秒，忽略 Retry-After，不进升级梯。
2. **+27~+32 日额已尽**（rpdExhausted/tpdExhausted）→ 升级梯 `getNextCooldownDuration`（2m→10m→…→24h 阶梯）。
3. **+36~+46 无日额发布时的启发**：`unknownLimits && quotaSignal` 时记 `recordNullLimitHit`，1 小时内 **≥2 次真 429** 视同日尽。`quotaSignal` 门是 #592 修复：过去 timeout/5xx 也喂这个计数器，两个慢生成就能把 null-limits 路由从 2m 一路升级——**只有 rate-limit 类错误才算配额证据**。启发出来的天花板 `UNKNOWN_LIMIT_MAX_COOLDOWN_MS` 封顶（猜的不许 bench 过死）。
4. **+48~+55 Retry-After 只当 floor**：`retryAfter > base` 才延长（封顶 24h、标 authoritative）；比 base 短**不缩短也不转 authoritative**——超出 provider 明示时长的部分仍是我们的猜测。

**调用方**：`cooldownDecisionForError`（fallback-loop 的错误分类学）→ `recordRetryableFailure+94` → `setCooldown`（内存 map + `persistCooldown` upsert 三列联合主键行）。

## 7. `runFallbackLoop` / `runFallbackLoopAttempts` — 回退主循环（fallback-loop.ts:1336/1355）

```ts
export async function runFallbackLoop(hooks: FallbackHooks): Promise<void>
// hooks 契约：route(attempt)→RouteResult | throw RouteError
//            dispatch(route, attempt, {disarmHedge}) → 响应写出去
//            state: FallbackState  onExhausted / onRoutingExhausted / logFailure
//            clientGone() abortInFlight() breakerLimit? maxRetries? timeBudgetMs?
```

**外壳**（`runFallbackLoop+11~+16`）：建 `RequestTrace`、`runWithRequestTrace`（AsyncLocalStorage）包住真循环，`finally` 里 `persistRequestAttempts(trace)` 一次性落 `request_attempts`——trace 在 dispatch 闭包深处由 `logRequest` 回填行 id，**任何 wire 面不用改一行代码**；flush 在响应结束后，不占客户延迟路径。

循环体分步（`runFallbackLoopAttempts+1~+180`）：

1. **+3~+14 初始化**：`maxRetries`(默认 20)、`baseBudgetMs`（三源优先级见 06 篇 §4.1）、`keyOrdinal` 给每个 (platform,key) 编序号（attempt trail 里区分同 key 复用）。
2. **+23~+38 熔断器**：默认关；第 N 次连续上游失败直接 503 终止（成功即结束循环，所以「一次请求内所有失败天然连续」）。auth 失败也计数——「一墙死 key」正是该早停的场景。
3. **+40~+43 clientGone**：客户断线即 return——不烧任何配额、无 socket 可渲染。**每个迭代头都查**。
4. **+45~+70 `hooks.route(attempt)` 抛错**（池子空）：若 base 预算已耗尽**保留原 timeout 诊断**（+50~+58：新端点的宽限不该抹掉「其实是被预算拖死」的真相）；零尝试时 `logRoutingExhaustion` 打印 routeRequest 攒的 per-model 处置行。
5. **+74~+90 预算检查在路由之后**：先选到端点，再按该端点的历史 TTFB 加宽预算（`getEndpointTimeBudgetMs`，**每个候选独立从 base 重算**——慢端点的宽限不许泄漏给梯子后面的快端点，但起点仍是循环入口）。attempt 0 和首次重试豁免（#751：首跳独占全部预算时，拒第二跳等于对最需要 failover 的请求结构性关死 failover）。
6. **+120~+144 hedge timer**：预算将满时给**静默窗口**装一个 `abortInFlight` 定时器；dispatch 一证明活着（首字节/headers 已刷）就 `disarmHedge`——**committed 的流杀了只会截断健康响应，慢 ≠ 卡死，只有卡死值得杀**。
7. **+150~+152 dispatch**：`withKeyProxy(route.proxyUrl, …)`——per-key 代理经 AsyncLocalStorage 传到 `proxyFetch`（#590），URL 已在路由期解好密。
8. **五个失败出口的语义**（这是整个函数的心脏）：
   - `isClientAbortError`（+158~+171）：自家客户挂断——零 bench 零统计，但补一行 `status='canceled'` 的 requests 可见性行（#752：纯 abort 过去在仪表盘上完全不留痕）。
   - `isHedgeAbortError`（+192~+207）：预算耗尽的在飞中止——**只有本跳自己沉默了 ≥75% 全预算**（`HEDGE_BENCH_MIN_SILENT_FRACTION`）才 bench 该路由；排在梯子末尾继承残羹的被杀是排程事故，不是路由病。然后渲染 timedOut 耗尽。
   - `isKeyAuthError`（+210~+217）：**KEY 致命不请求致命**——`recordAuthFailure` 轮换下一把 key 并即时重验证，continue。
   - `isRetryableError`（+220~+240）：`recordRetryableFailure` 记账（§8）；迟到 ≥75% 预算的 in-band provider 错误（#1218 Gap 3：nvidia 沉默 140.7s 才报 overloaded）补上 hedge-bench 同款处置——**晚到的错误和卡死一个待遇，早到的判决（Groq tool_use_failed 形态）不 bench**。
   - 其余（非 retryable 的 4xx 等）：fatal，走 logFailure + 停链渲染。

**调用方**：`/v1/chat/completions`、responses、anthropic、gemini、ollama、messages/count_tokens 各面的 handler 全部把归一化后的请求包成 hooks 交给这一个循环（05 篇「契约收敛」的实体）。

## 8. `recordRetryableFailure` — 失败分类学（fallback-loop.ts:438）

```ts
export function recordRetryableFailure(route, err, state: FallbackState,
                                       now = Date.now()): boolean
// true = 豁免 bench（消费了 skipBench 豁免），false = 正常处置
```

**职责**：把一次失败翻译成对 skipModels / skipPlatforms / skipKeys / cooldown / penalty / learned-limits 六种状态的最小正确变更。分类顺序即裁决逻辑（`recordRetryableFailure+8~+100`）：

1. **+8~+11 模型行为级**：404 removed / 403 forbidden / context-too-large / `skipModelForRequest`——**兄弟 key 会逐字复现**，整模型对本请求出局。
2. **+20~+30 目录级联**（#1218）：同平台**不同模型**的 DISTINCT model_not_found ≥ 阈值 ⇒ 整个平台出局（NavyAI 一个 session 24 模型 0 成，每 miss 重付 2.5-10s——per-model skip 看不见模式）。`endpointScope` 非空的 custom relay 豁免：所有 relay 共享 platform id 'custom'，三个 miss 跨三个 relay 会把健康的也一锅端。
3. **+36~+41**：模型级 404/410 的「gone」信号过证据阈值后**持久化**（`noteModelRetirementSignal`，#634）——退役模型否则永远占一个回退槽。
4. **+44~+54 请求尺寸学习**（#507）：413/bad-request 里解析出真实 token 数 ⇒ `observedTotalTokens/observedInputTokens` **只增不减**，下一次 `hooks.route` 用它当估算，让低上限模型在重试时被路由层预先跳过。
5. **+57~+64 provider 级**：5xx/timeout/transport/502 ⇒ 整平台出局（#788：病的是 provider，不是 key；逐 key 烧尝试毫无意义）。**唯一跨请求的状态仍是 per-key 冷却**。
6. **+66~+78 无罪学习**：context-too-large = **请求的属性不是模型的病**——learn 上限、本请求跳过，**零 cooldown 零 penalty**（bench 的后果：一个 16k-token 的 agent 轮能把所有小 TPM 模型沉底，后续普通请求看到满池 rate limited）。同理 max_tokens 超输出上限（+81~+91）：学到新上限 ⇒ 撤销本 key 的 skip 立刻复用；上限早已生效还被拒 ⇒ 模型出局。
7. **+93~+94**：过完无罪层才轮到期——`consumeSkipBenchExemption`（格式被忽略等豁免类）→ `cooldownDecisionForError` → `setCooldown(decision.source)`。
8. **+96~+100+ 连坐**：截断流/空完成按 streak（同一 route 连续 N 次才 bench 一个冷却窗，一次不算病）；`benchKeyAcrossPlatform`（+131）把坏 key 在它平台的**每个模型**上连坐 bench——auth 失败、解密失败是 key 属性，与模型无关。

## 9. `getWindow` 族 — 内存滑窗基元（ratelimit.ts:18/27）

```ts
getWindow(key) → {timestamps: number[], tokenTimestamps: {ts, tokens}[]}
pruneTimestamps(timestamps, windowMs, now) → number[]
```

`windows` 是模块级 `Map<string, Window>`（key 形如 `platform:model:keyId:rpm|rpd|tpm|tpd`），`memoryRequestCount` = prune 后长度、`memoryTokenCount` = 窗口内 reduce 求和。**它只在无 DB 时是真相**（§5 第 2 步），有 DB 时 `pushMemoryRequest/Tokens` 仍在写入——两套计数器并行，读侧 DB 优先。设计不变量：**窗口以 `created_at_ms` 毫秒整数为准，UTC 日界用 `msSinceUtcMidnight`**，与 provider 的「每日」语义（Pacific 重置的平台由 `msUntilNextPacificMidnight` 服务）。
